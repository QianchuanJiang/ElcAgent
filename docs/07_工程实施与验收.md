# 07 · 工程实施与验收

> 本文定义模型选型与分层调度、技术栈、实施路径、验收标准与风险预案。

---

## 1. 模型选型与分层调度

### 1.1 分层依据

模型不是越强越好，而是**按任务性质匹配**。三档划分依据如下：

| 档位 | 承担的任务 | 任务特征 | 对模型的要求 |
|---|---|---|---|
| **重档** | 复杂研判、方案生成、长文撰写 | 需跨案例推理、输出长 | 推理能力强、上下文长 |
| **轻档** | 意图识别、结构化抽取、查询改写 | 高频、简单、输入输出短 | 延迟低、成本低 |
| **多模态** | 图像判读 | 输入为图像 | 图像理解能力 |
| **向量 / 重排** | 记忆检索与案例召回 | 高并发、确定性 | 稳定、可本地化 |

**关键原则**：**数值计算不进模型**。所有确定性物理公式由代码执行。模型只在两处介入——语义解析（如预警报文理解）与语义修正（结合历史案例调整风险权重，权重占比 20%）。

### 1.2 候选模型矩阵

| 档位 | 模型 | 用途 | 部署形态 |
|---|---|---|---|
| 重档 | GLM 系列大参数版本 | 复杂研判、方案生成、简报撰写 | 本地私有化（需 GPU）或兼容接口 |
| 中档 | GLM 系列中等参数版本 | 作为重档的成本优化替代 | 本地单卡可运行 |
| 轻档 | GLM Flash 系列 | 意图识别、结构化抽取、查询改写 | 兼容接口，延迟低 |
| 多模态 | GLM 视觉版本 | 监拍图像判读 | 兼容接口或本地 |
| 向量 | 通用中文嵌入模型 | 记忆与案例向量化 | **建议本地运行**，数据不出机 |
| 重排 | 通用交叉编码器重排模型 | 检索结果重排 | 建议本地运行 |

### 1.3 三档部署形态

| 档位 | 配置 | 适用场景 | 取舍 |
|---|---|---|---|
| **A · 全本地** | 本地推理运行时 + 本地嵌入与重排 | 演示「数据不出域」叙事；离线环境 | 延迟较高，模型能力受显存限制 |
| **B · GPU 私有化** | GPU 服务器 + 本地大模型 + 本地嵌入 | 需要高质量长文生成 | 需要 GPU 资源 |
| **C · 混合（推荐默认）** | 轻档走兼容接口，重档走本地或接口，嵌入与重排本地 | 日常开发迭代 | 兼顾速度与成本 |

**推荐默认档位为 C**：轻任务走接口（快、便宜），重任务按需切换，嵌入与重排保持本地（数据不出机，契合私有化叙事）。全本地 A 档保留为**可切换选项**，用于演示数据不出域的能力。

### 1.4 ModelRouter 抽象

**唯一约束：业务代码不感知模型来源，只声明任务档位。**

```yaml
model_router:
  profiles:
    local:
      heavy:  { provider: local_runtime, model: <重档本地模型> }
      light:  { provider: local_runtime, model: <轻档本地模型> }
      vision: { provider: local_runtime, model: <视觉模型> }
      embed:  { provider: local,         model: <本地嵌入模型> }
    hybrid:
      heavy:  { provider: compat_api,    model: <中/重档模型> }
      light:  { provider: compat_api,    model: <轻档模型> }
      vision: { provider: compat_api,    model: <视觉模型> }
      embed:  { provider: local,         model: <本地嵌入模型> }

  routing_rules:
    - match: { agent: <会话网关> }                    -> light
    - match: { agent: <风险研判>, phase: semantic }    -> heavy
    - match: { agent: <图像判读> }                     -> vision
    - match: { task: memory_embed }                    -> embed

  fallback:
    on_timeout_ms: 20000
    chain: [heavy_local, light_local, rule_template]
```

| 路由对象 | 档位 | 理由 |
|---|---|---|
| 意图识别、参数补全 | light | 简单分类，要求低延迟 |
| 数值物理计算 | **none** | 确定性公式，用模型既浪费又不可审计 |
| 风险语义修正与归因 | heavy | 需跨案例推理 |
| 简报撰写 | heavy | 长文本生成质量敏感 |
| 监拍判读 | vision | 多模态专属 |
| 记忆向量化 | embed | 专用模型 |

### 1.5 实施注意事项

| # | 事项 | 说明 |
|---|---|---|
| 1 | 推理型模型需留足输出预算 | 部分模型会先输出思考内容再输出答案。若输出预算被思考过程耗尽，正式内容将为空。**输出预算需显著大于预期答案长度** |
| 2 | 思考内容单独处理 | 思考内容与正式答案分属不同字段，应分别解析。思考过程本身可作为「智能体正在推理」的可视化素材 |
| 3 | 结构化输出需校验 | 所有模型输出走 schema 校验；失败自动重试 1 次（附带错误信息），再失败降级到模板 |
| 4 | 数值禁止由模型生成 | 数值类结论必须来自技能返回值，模型只能引用不能编造；输出后做范围校验 |
| 5 | 术语表强制注入 | 领域术语从语义记忆注入，避免同义词混用导致口径不一致 |
| 6 | 密钥只走环境变量 | 不硬编码进代码或配置文件；仓库提供模板文件，真实值不入库 |

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11+ | 异步与类型特性 |
| Web 框架 | FastAPI + ASGI 服务器 | 原生异步，适合长连接与流式 |
| 数据校验 | Pydantic v2 | 契约层统一 |
| 编排运行时 | 自研轻量运行时（异步） | 见下方说明 |
| 消息总线 | 进程内异步事件总线（可换 Redis Streams / NATS） | 信封协议与传输解耦 |
| ORM | SQLAlchemy 2.x | 屏蔽数据库差异 |
| 关系库 | SQLite（开发）/ PostgreSQL（生产） | 通过 ORM 屏蔽差异 |
| 向量库 | 本地向量库 或 pgvector | 与关系库合一可简化部署 |
| 推理运行时 | 本地推理服务 / 兼容接口 | 由 ModelRouter 配置切换 |
| 定时任务 | 调度库 | 记忆衰减与巩固 |
| 日志 | 结构化日志库 | 便于审计聚合 |
| 前端 | React 18 + TypeScript + Vite | — |
| 样式 | TailwindCSS + 组件库 | 快速产出高质感界面 |
| 图表 | ECharts | 地图、曲线、桑基图 |
| 图可视化 | React Flow | 拓扑与因果树 |
| 地图 | MapLibre + 离线行政区划数据 | 无 token 依赖，合规 |
| 容器化 | Docker Compose | 一键启动 |

### 2.1 为什么自研编排运行时而不直接用现成框架

现成框架（如状态图类框架、对话式多智能体框架）适合快速原型，但本项目有两条硬要求：

| 要求 | 说明 |
|---|---|
| 消息级审计留痕 | 每条消息需携带业务字段（置信度、引用的记忆、调用的技能、模型档位）并完整落库 |
| 责任可追溯的仲裁链 | 需要显式的仲裁记录与降级路径，而非框架内部的隐式流转 |

自研运行时在这两点上完全可控，且架构上保留了替换可能——信封协议与运行时实现解耦，未来可局部替换为成熟框架的组件。

## 3. 实施路径

**核心原则：先机制，后内容。**

不先铺业务数据，而是先把三个核心模块的机制跑通。原因是：机制骨架才是本项目真正的目标产物，业务数据只是让骨架可被观察的载体。

### 3.1 三阶段

| 阶段 | 内容 | 产出 | 不需要的东西 |
|---|---|---|---|
| **一 · 打通机制** | 1 个主控 + 1 个执行智能体 + 3 个技能 + 1 条记忆的完整生命周期 | 可运行的最小骨架：能看到消息在跑、记忆在写、技能在被调度 | **不需要任何业务数据** |
| **二 · 扩展复杂度** | 8 个智能体 + 20 个技能 + 三层记忆 + 并发 + 仲裁 + 熔断 | 完整协同链路 + 两个核心前端页面 | 不需要完整业务数据 |
| **三 · 补齐内容** | 业务数据、规则包、简报模板、其余前端页面 | 可演示完整系统 | — |

**阶段一的最小骨架由五个模块构成**：

| 模块 | 职责 |
|---|---|
| 消息总线 | 信封定义 + 事件总线 + 路由表 |
| 记忆模块 | 记忆表 + 向量检索 + 写入去重 |
| 技能模块 | 注册表 + schema 校验 + 调用日志 |
| 智能体模块 | 主控动态生成执行图 + 一个执行智能体 |
| 自检脚本 | 下方验证清单的自动化版本 |

**建议**：把这五块先跑通，再往里灌业务。这样即使业务数据全是模拟的、模型全部用规则替代，三个核心模块依然是真实的。

### 3.2 关键路径

- **关键路径**：契约冻结 → 记忆机制 → 通信机制 → 技能治理 → 业务智能体 → 前端
- **可并行**：前端在接口契约冻结后即可并行开工（可用模拟事件流驱动）
- **必须先冻结**：消息信封、Agent Card 规范、技能注册表格式。这三者冻结前不进入并行开发，否则后期改动代价极大

## 4. 验收标准

### 4.1 三组模块验证清单（共 15 条）

「实现了」与「可证明实现了」是两件事。以下每条都是**证伪测试**——全部通过才算机制真的落地。

**记忆模块（5 条）**

| # | 验证项 | 通过标准 |
|---|---|---|
| 1 | 关闭记忆重跑同一任务 | 耗时 / 调用次数 / token 明显变差 |
| 2 | 手动修改一条记忆的内容后重跑 | 结论跟着变化 |
| 3 | 注入两条冲突记忆并仲裁 | 系统行为改变，且旧版仍可查 |
| 4 | 查询某条记忆的访问日志 | 能看到「谁在何时因何查询命中了它」 |
| 5 | 把某条记忆的最近访问时间往前调 | 其检索排序下降 |

**通信模块（5 条）**

| # | 验证项 | 通过标准 |
|---|---|---|
| 6 | 从一条 trace 重建因果树 | 父子关系完全正确 |
| 7 | 故意让某智能体超时 | 看到重试 → 降级 → 状态变更的完整过程 |
| 8 | 制造同一三元组往返 3 次 | 被强制中断，不进入死循环 |
| 9 | 两个智能体同时写黑板同一键 | 占有机制生效，无数据错乱 |
| 10 | 广播一个事件 | 多个订阅者都收到，且互不阻塞 |

**技能模块（5 条）**

| # | 验证项 | 通过标准 |
|---|---|---|
| 11 | 传非法参数 | 被 schema 拒绝，错误信息可读 |
| 12 | 白名单外的智能体调用 | 被拒并留下审计记录 |
| 13 | 禁用某个技能 | 任务走完整降级链 |
| 14 | 相同入参调用两次 | 第二次缓存命中 |
| 15 | 超过限流阈值 | 被限流，且不阻塞主链路 |

**建议**：把这 15 条做成自动化自检脚本，每次改动后跑一遍。它比文档有效得多——**会在机制被写假的时候报警**。

### 4.2 系统级验收标准

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 预警端到端全自动研判 | 一条指令触发，无人干预产出风险清单 |
| 2 | 数据口径映射生效 | 多套历史编码归并为统一标准编码，映射日志可查 |
| 3 | 数据质量问题被拦截 | 异常记录被隔离并给出原因 |
| 4 | 风险清单可解释 | 每条含多个风险因子及贡献度 |
| 5 | 短期记忆跨轮次保持 | 同一会话后续轮次仍记得前序约束 |
| 6 | 长期记忆跨会话生效 | 新会话复用已沉淀的处理路径与口径 |
| 7 | 用户记忆个性化可见 | 切换用户后输出风格 / 默认辖区 / 模板变化 |
| 8 | 记忆可解释 | 任一结论可展开引用的记忆清单与得分 |
| 9 | 多智能体消息全程可见 | 消息时序完整，含言语行为类型与耗时 |
| 10 | 熔断与人工升级可演示 | 置信度低于阈值时自动生成人工待办 |
| 11 | 简报自动生成 + 溯源 | 简报每段标注引用来源 |
| 12 | 全链路审计可回溯 | 任一结论可下钻至消息 / 技能 / 记忆 / 数据 / 模型版本 |

### 4.3 需要主动说明的边界

验收时不回避以下事实，主动说明反而更能建立专业信任：

| 项 | 说明 |
|---|---|
| 记忆的效果 | 主要提升效率与一致性，**不改变确定性物理计算的结果** |
| 模型的作用范围 | 只用于语义解析与语义修正（权重约 20%），数值计算全部由代码完成 |
| 数据的性质 | 模拟数据仅用于调试与功能测试，不作为能力评估依据 |
| 与生产系统的差距 | 见下节 |

## 5. 风险与降级预案

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 模型推理延迟高 | 演示等待时间长 | 流式输出；高频调用预热缓存；准备回放模式；关键节点用确定性模板兜底 |
| 2 | 模型编造数值 | 结论不可信 | 数值只能来自技能返回值；输出做 schema 与范围双重校验 |
| 3 | 状态被反复操作后变脏 | 演示不可复现 | 提供重置到基线命令，从固定快照恢复 |
| 4 | 多智能体并发写冲突 | 数据错乱 | 命名空间隔离 + 占有机制 + 超时释放 + 冲突留痕 |
| 5 | 检索效果不佳 | 命中不相关记忆 | 提高重排权重；增加元数据硬过滤；预置高质量初始记忆 |
| 6 | 复杂度失控 | 交付延期 | 严格按阶段推进；契约先冻结；明确的裁剪清单 |
| 7 | 地图与地理数据合规 | 合规风险 | 只渲染离线行政区划数据，不使用边界存疑的底图 |
| 8 | 需求边界模糊导致范围蔓延 | 项目失焦 | 以第 4 节验收标准为唯一判据 |

### 5.1 裁剪优先级（时间不足时按此顺序砍）

| 顺序 | 砍掉的 | 影响 |
|---|---|---|
| 1 | 多模态图像判读 | 少一个能力点，可人工替代 |
| 2 | 非覆冰场景（大风 / 雷暴） | 只保留单一灾害类型 |
| 3 | 重排模型 | 直接用融合结果注入 |
| 4 | 简报导出文档 | 仅页面展示 |
| 5 | 智能体数量从 15 精简到 8 | 架构展示略简化 |

**绝对不可砍的四项**：记忆系统、消息可视化、溯源下钻、用户切换。这四项是机制可验证性的来源，砍掉之后项目就退化成普通业务系统。

## 6. 与生产环境的差距

本项目为**能力验证型系统，不可直接用于工业生产**。工业落地还需补齐：

| # | 前置工作 | 说明 |
|---|---|---|
| 1 | 真实数据接入与脱敏管道 | 对接真实业务系统，建立脱敏与授权流程 |
| 2 | 统一身份认证对接 | 接入企业统一权限中心，替代静态角色配置 |
| 3 | 安全加固 | 传输加密、审计防篡改、密钥管理、输入防护 |
| 4 | 高可用与可运维 | 多实例部署、限流降级、监控告警、灰度发布 |
| 5 | 评测质量升级 | 建立标注数据集与量化评测体系；当前仅做机制验证 |
| 6 | 合规与审计体系 | 满足行业安全生产的可追溯与留痕要求 |
| 7 | 模型与算力规划 | 私有化算力池、并发削峰、模型版本管理 |

其中第 1、2、6 项是接入真实环境的关键路径；第 4 项决定系统能否稳定运行；第 5 项决定系统能否被信任。
