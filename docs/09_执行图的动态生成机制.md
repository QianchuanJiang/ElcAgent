# 09 · 执行图的动态生成机制

> 本文定义主控调度如何根据任务生成执行图。这是整个内核中最容易被做成假的地方，因此本文把每一步都落到**确定性、可验证**的机制上。

---

## 1. 问题

「主控调度按任务动态生成执行图」这句话听起来很直观，但实现上有四种走法，只有一种是真正的动态编排：

| 走法 | 实质 | 判定 |
|---|---|---|
| DAG 写死成顺序调用 | 工作流引擎 | ❌ 无编排 |
| 每个意图硬编码一条固定链路 | 变相写死 | ❌ 有分支无生成 |
| **让模型自由生成计划与执行者** | 看起来最"智能" | ❌ 会幻觉出不存在的智能体，不可验证 |
| **模板为主 + 模型兜底 + 校验器把关** | 生成过程可审阅 | ✅ 本文采用 |

第三种走法最诱人，也最危险：模型生成的智能体名字可能根本不在注册表里，链路可能违反权限，成本无法预估。**一个无法验证的调度器比一个简单的调度器更糟。**

---

## 2. 核心设计：三个阶段，模型只负责第一阶段

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段一 · 意图识别与参数填充        【模型参与】               │
│   自然语言 / 事件内容 → 受控意图 + 结构化参数                 │
│   模型的唯一职责：理解人话，不负责决定谁来干活                 │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段二 · 能力需求推导与执行者选择   【纯查表，确定性】         │
│   意图 → 能力需求模板 → 能力集合                              │
│   能力集合 → Agent Registry 能力索引 → 候选智能体             │
│   候选 → 按约束过滤（权限/深度/预算）→ 入选集合                │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 阶段三 · 依赖推导与图生成          【纯计算，确定性】         │
│   各能力声明输入输出 → 求数据依赖 → 拓扑排序 → 生成 DAG        │
│   无依赖的能力自动并行                                        │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
                    ┌──────────────┐
                    │  契约校验器   │  ← 不合规的图直接拒绝执行
                    └──────────────┘
```

**关键原则：模型只在阶段一出现。阶段二、三完全是确定性的查表与计算。**

这样做的三个收益：

| 收益 | 说明 |
|---|---|
| 可验证 | 能力模板是静态配置，可人工审阅、可 diff、可回归测试 |
| 不幻觉 | 模型无法凭空造出注册表里不存在的智能体 |
| 可演进 | 新增智能体只改配置，调度逻辑零改动 |

## 3. 阶段一 · 意图识别与参数填充

### 3.1 意图是受控词表，不是自由生成

模型输出的意图必须落在预定义枚举内，不允许自由发挥。理由：意图是后续所有路由的键，自由文本无法作为键使用。

| 意图 | 语义 | 典型入口 |
|---|---|---|
| `risk_assessment` | 灾害风险研判 | 预警事件 / 用户提问 |
| `point_query` | 单点状态查询（某区段当前如何） | 用户提问 |
| `root_cause` | 归因分析（为什么会这样） | 用户追问 |
| `plan_solve` | 处置方案求解 | 研判结果下游 |
| `brief_generate` | 简报生成 | 定时任务 / 用户请求 |
| `data_check` | 数据质量核查 | 运维请求 |
| `config_update` | 配置更新（阈值、订阅规则） | 用户指令 |

### 3.2 参数填充的约束

模型填充的参数同样受 schema 约束，越界即拒绝：

| 参数 | 类型 | 约束 |
|---|---|---|
| `scope` | 区段/线路集合 | 必须能解析为真实主数据，且在当前用户权限范围内 |
| `time_window` | 时间区间 | 不得超出数据可用范围 |
| `disaster_types` | 枚举数组 | 必须是受支持的灾害类型 |
| `depth_hint` | L0/L1/L2 | 可选，缺省时由意图与优先级推导 |

**参数解析失败的处理**：不猜测、不降级为"全部"，而是**反问用户**。猜测范围会产生"看起来答了但答错了"的后果，比直接反问更糟。

### 3.3 意图识别的失败路径

| 情况 | 处置 |
|---|---|
| 置信度低但匹配到某意图 | 执行，但在回复中标注"按 X 意图处理，如不符请纠正" |
| 完全无法匹配意图 | 走兜底意图 `point_query`，或用解释性回答（不进入执行链） |
| 匹配到多个意图 | 按优先级选一个，或拆分为多个任务 |

## 4. 阶段二 · 能力需求推导与执行者选择

### 4.1 为什么用「能力」而不是直接选智能体

这是本文最核心的一个设计决定。

| 方案 | 优点 | 致命问题 |
|---|---|---|
| 直接选智能体 | 一步到位 | 智能体会增删改，链路随之失效；模型容易幻觉出不存在者 |
| **先推导能力，再由能力索引映射到智能体** | 能力稳定、模板可审阅、可验证 | 多一层间接 |

「能力」（capability）是稳定的抽象，「智能体」是它的一个实现。同一个能力可以由不同智能体提供（例如拆分的精简版与完整版），也可以有备选实现用于降级。

### 4.2 能力需求模板

每个意图对应一张模板，模板是**配置而非代码**：

```yaml
intent: risk_assessment
requires:
  - capability: data_governance
    mode: required
  - capability: meteo_analysis
    mode: required
  - capability: asset_spatial
    mode: required
  - capability: rule_evaluation
    mode: required
  - capability: risk_scoring
    mode: required
  - capability: history_retrieval
    mode: conditional
    when: { depth_gte: L1 }
  - capability: confidence_review
    mode: conditional
    when: { depth_gte: L1 }
  - capability: vision_inspection
    mode: conditional
    when: { has_artifact: camera_snapshot }
  - capability: memory_retrieval
    mode: conditional
    when: { depth_gte: L1 }
```

| 模式 | 语义 | 缺失时 |
|---|---|---|
| `required` | 必需 | 无法满足则任务失败（不允许静默降级） |
| `conditional` | 条件启用 | 条件不满足则跳过，不视为失败 |
| `optional` | 可选增强 | 可用则启用，不可用不影响主链路 |

**`conditional` 是本设计中"动态性"的主要来源**：同一个意图，因为深度不同、有无监拍图、有无历史案例，最终选出的智能体集合不同。

### 4.3 从能力到执行者

Agent Registry 维护一张**能力 → 智能体**的反向索引：

```
capability: risk_scoring
providers:
  - agent: A07_risk_assessor
    priority: 1
    version: v1.2
  - agent: A07b_risk_assessor_lite      # 备选（降级用）
    priority: 2
    version: v1.0
```

选择规则（按序）：

| 顺序 | 规则 |
|---|---|
| 1 | 过滤掉不在候选能力提供者列表中的智能体 |
| 2 | 过滤掉超出任务权限的（`permission_scope` 高于当前角色） |
| 3 | 过滤掉超出执行深度上限的（该智能体要求的最低深度高于任务深度） |
| 4 | 过滤掉被禁用的（技能页可关闭某个智能体，用于验证降级） |
| 5 | 在同优先级的候选中按负载与预算选择 |
| 6 | 若无可用提供者且该能力为 `required` → 任务失败并说明原因 |

### 4.4 当模板匹配失败时

模板覆盖不了所有情况。三种例外：

| 例外 | 处置 |
|---|---|
| 意图无法匹配任何模板 | 由模型生成候选能力集合，**但必须通过校验**（只能引用注册表中存在的能力） |
| 模板匹配但参数组合异常 | 先尝试按 `optional` 模式放宽；仍异常则反问用户 |
| 用户显式要求某能力 | 走"用户指定通道"：跳过模板推导，直接按用户指定的能力集合构建，但仍需通过权限与深度校验 |

**校验器的三条铁律**：① 能力必须存在于注册表；② 智能体必须有权执行该能力；③ 结果图必须无环。

## 5. 阶段三 · 依赖推导与图生成

### 5.1 依赖从数据依赖算出来，不是猜出来的

每个能力声明它的输入需求与输出产物：

```yaml
capability: risk_scoring
inputs:  [meteo_features, candidate_spans, rule_hits, similar_cases]
outputs: [risk_ranking]

capability: rule_evaluation
inputs:  [candidate_spans, rule_pack]
outputs: [rule_hits]

capability: meteo_analysis
inputs:  [meteo_timeseries]
outputs: [meteo_features]
```

推导规则（完全确定性）：

```
若 A.outputs ∩ B.inputs ≠ ∅  则  B 依赖 A（B 必须等 A 完成）
若 A.outputs ∩ B.inputs = ∅  则  A 与 B 可并行
```

对能力集合做拓扑排序，得到执行图。**无依赖的能力自动并行，不需要人工指定。**

### 5.2 这个过程的可验证性

| 性质 | 如何检验 |
|---|---|
| 无环 | 拓扑排序若失败即证明存在环，校验器拒绝 |
| 完备 | 每个 `required` 能力的输入，必须能由某个入选能力的输出或外部数据源满足；否则图不完整 |
| 最小 | 入选集合中不应存在"输出无人消费、且自身非终态产出"的能力 —— 可自动剪枝 |
| 可解释 | 每条依赖边都能回答"为什么连这条线"（因为 A 的输出是 B 的输入） |

**「可解释」这一条尤其重要**：依赖边不是模型"觉得应该有"，而是两个声明的输入输出集合的交集。任何人都能复核。

### 5.3 三种深度下的图差异

以 `risk_assessment` 为例，同一意图在三个深度下生成的图截然不同：

| 深度 | 入选能力 | 图形态 |
|---|---|---|
| L0 | 治理 · 气象 · 空间 · 规则 | 纯计算并行，4 节点无模型调用 |
| L1 | L0 + 案例召回 · 风险打分 · 置信度评审 · 记忆检索 | 两段式：并行基础计算 → 汇聚打分 → 评审 |
| L2 | L1 + 方案生成 · 简报撰写 · 审计固化 + 审批 | 三层：研判 → 方案 → 产出与签发 |

**同一意图、三张不同的图**——这就是动态生成的直接证据。如果三张图完全一样，说明是写死的。

### 5.4 并行度的确定

| 组 | 并行策略 |
|---|---|
| 无相互依赖的能力 | 全部并行发起 |
| 有并发上限的能力 | 按 `max_concurrency` 排队 |
| 汇聚节点（如风险打分） | 等所有上游完成后再启动（Join 语义） |
| 条件能力 | 条件求值后再决定是否加入图 |

**汇聚节点的等待语义要明确**：默认是"全部成功才继续"；若某个上游失败，则按第 6 节的局部重规划处理，而不是无限等待。

## 6. 运行期动态调整：局部重规划

前面三节解决的是「首次规划」。真正的动态还包含**执行过程中图的变化**。

### 6.1 触发重规划的四种情况

| 情况 | 触发 |
|---|---|
| 节点失败 | 执行返回 `FAILURE` 且重试后仍失败 |
| 节点降级 | 降级层级超过阈值（结果质量不可接受） |
| 数据前置不满足 | 条件能力的条件在运行期变为假 |
| 预算耗尽 | 剩余预算不足以完成剩余节点 |

### 6.2 重规划的五步

```
① 确定影响域：失败节点的全部下游节点（沿依赖边正向可达集合）
② 查找替代：该能力是否有备选提供者？降级链能否继续？
③ 判断可续性：
     可续 → 替换执行者，只重跑影响域（已完成的上游不动）
     不可续 → 剪枝，把影响域内所有产出标记为"依据不完整"
④ 重算置信度：受影响产出的置信度按缺失的输入项数衰减
⑤ 交出决定权：由置信度评审决定 —— 通过 / 熔断 / 请求人工
```

### 6.3 为什么不整图重来

| 整图重来的代价 | 局部重规划的收益 |
|---|---|
| 丢失已完成的全部工作 | 已完成的上游结果直接复用 |
| 成本与耗时翻倍 | 只重跑受影响子图 |
| 两次执行的中间结果不一致，审计无法解释 | 一次任务只有一条执行轨迹，审计链完整 |

**「审计链完整」是最关键的理由**——如果一次任务实际执行了两遍，那份 trace 就无法回答"最终结论是按哪一次的执行结果得出的"。

### 6.4 重规划的边界

| 约束 | 说明 |
|---|---|
| 最多重规划 1 次 | 第二次仍失败则升级人工，防止无限重试 |
| 不得改变任务意图 | 只调整执行者与子图，不改 `intent` |
| 不得放宽约束 | 不能为了提高成功率而突破权限或深度上限 |
| 必须留痕 | 每次重规划落 `replan_record`，含触发原因、影响域、替换方案 |

## 7. 契约校验器

**执行图在提交执行前必须通过校验器。** 校验失败的任务不执行，直接返回原因。

| # | 校验项 | 失败处置 |
|---|---|---|
| 1 | 所有引用必须存在于注册表 | 拒绝（防止幻觉） |
| 2 | 所有 `required` 能力都有可用提供者 | 拒绝并说明缺失能力 |
| 3 | 依赖图无环 | 拒绝 |
| 4 | 每个节点的输入都可达（由上游产出或外部数据源提供） | 拒绝并指出缺口 |
| 5 | 智能体权限不超出任务角色 | 拒绝（防止越权） |
| 6 | 节点深度不超过任务深度上限 | 拒绝（防止成本失控） |
| 7 | 预估预算不超过任务预算 | 拒绝或请求提额 |
| 8 | 终态产出与意图匹配（如 `brief_generate` 必须产出简报） | 拒绝 |

**校验器是"可验证性"的最后一道闸门。** 有了它，才敢说"调度器是可信的"；没有它，动态生成就是一个不可控的黑盒。

## 8. 数据结构

### 8.1 执行图节点

| 字段 | 说明 |
|---|---|
| `node_id` | 节点标识 |
| `capability` | 所需能力 |
| `agent_id` | 实际执行者 |
| `depends_on` | 依赖的节点集合 |
| `inputs` / `outputs` | 声明的输入输出 |
| `condition` | 条件（条件能力专用） |
| `budget` | 该节点的超时与 token 上限 |
| `parallel_group` | 可并行的分组标识 |
| `fallback` | 降级目标（备选提供者） |

### 8.2 规划记录

| 表 | 内容 |
|---|---|
| `plan_record` | 每次规划的输入（意图、参数、深度）与输出（图结构、入选智能体、依据） |
| `replan_record` | 重规划触发原因、影响域、替换方案、重规划前后图差异 |
| `plan_rejection` | 被校验器拒绝的图及拒绝原因（用于观察幻觉与配置错误） |

**`plan_rejection` 这张表在开发期价值极高**——它直接暴露"模型幻觉出了不存在的智能体"这类问题。生产期则是配置错误的第一现场。

---

## 9. 反例：什么算是「假」的动态生成

| # | 反例 | 为什么是假的 |
|---|---|---|
| 1 | DAG 写死成顺序调用 | 没有编排，只是工作流引擎 |
| 2 | 每个意图硬编码一条固定链路 | 有分支但无生成，等价于写死 |
| 3 | 让模型自由生成执行者列表 | 会幻觉、不可验证、成本不可控 |
| 4 | 只有首次规划，运行期从不调整 | 只是静态规划 |
| 5 | 重规划时整图重来 | 丢失已完成工作，审计链断裂 |
| 6 | 没有校验器，生成什么就执行什么 | 不可控黑盒 |
| 7 | 依赖关系由模型"判断" | 无法复核，无法解释 |

---

## 10. 验证清单

| # | 验证项 | 通过标准 |
|---|---|---|
| 1 | 同一意图在不同深度下生成的图不同 | 三张图可 diff 出结构差异 |
| 2 | 同一意图在有无监拍图时生成的图不同 | 条件能力被正确启用/跳过 |
| 3 | 模型幻觉出不存在的能力 | 校验器拒绝，记入 `plan_rejection` |
| 4 | 依赖边可解释 | 每条边能指出它由哪组输入输出交集产生 |
| 5 | 无依赖能力确实并行 | 从 trace 可见时间重叠 |
| 6 | 让某节点失败 | 观察到局部重规划，已完成上游未被重跑 |
| 7 | 重规划两次仍失败 | 升级人工，不无限重试 |
| 8 | 关闭某智能体 | 图中不再出现，且按降级链找到备选或正确失败 |
| 9 | 权限不足的能力被请求 | 校验器拒绝 |
| 10 | 拓扑排序遇环 | 校验器拒绝，不进入执行 |
