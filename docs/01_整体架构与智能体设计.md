# 01 · 整体架构与智能体设计

> 本文定义系统的分层架构、智能体的声明式规范与编队、以及多智能体的编排模型。

---

## 1. 需求还原

### 1.1 业务场景

某省级电网企业的输电线路跨越覆冰、大风、雷暴等气象灾害高发区，防灾研判是设备运检与安全监督部门的核心职责之一。灾害预警到来时的一次典型处置包含六个环节：

```
① 气象预警下发
② 人工圈定可能受影响线路区段
③ 跨设备台账 / 气象 / 地理信息 / 缺陷库 / 微气象 / 图像监拍等多系统人工拉通数据
④ 派班组现场观测，或等待监拍回传判读
⑤ 制定融冰 / 避险方案，报安全监督部门审批
⑥ 手工撰写运维简报与灾情报告
```

### 1.2 待解决的结构性问题

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 数据割裂、口径不一 | 线路编码、时间粒度在各业务系统中不一致，人工拉通耗时长、易出错 |
| P2 | 研判依赖经验 | 极端天气下多线路同时告警时，人工逐线排查不可行，存在漏判风险 |
| P3 | 数据不出域约束 | 生产网与外部网络隔离，通用云端模型不可直连 |
| P4 | 简报手工制备 | 安全监督复盘要求可追溯，手工报告滞后于处置窗口 |
| P5 | 时效窗口短 | 研判延迟即错过提前融冰 / 避险的最佳时机 |

### 1.3 目标流程的替换点

| 现状环节 | 目标能力 | 承担智能体 |
|---|---|---|
| ① 预警下发 | 报文自动接入与语义解析 | 气象解析智能体 |
| ② 人工圈定区段 | 空间相交 + 微地形暴露度自动初筛 | 台账空间智能体 |
| ③ 人工拉通数据 | 口径统一后并行取数 | 数据治理智能体 |
| ④ 现场观测 / 监拍判读 | 监拍图像多模态自动判读 + 补拍建议 | 图像判读智能体 |
| ⑤ 制定方案并报审 | 方案候选生成 + 置信度门禁 + 待办推送 | 方案生成 / 置信度评审 / 审批协同 |
| ⑥ 手工撰写简报 | 模板化自动生成初稿 + 人工复核签发 | 简报撰写智能体 |

### 1.4 设计原则

| 原则 | 含义 | 架构上的体现 |
|---|---|---|
| 私有化优先 | 模型与数据全闭环，满足数据不出域 | 推理运行时与存储均可本地化，配置切换 |
| 数据治理先行 | 先统一口径与质量校验，再喂模型 | 治理作为独立智能体 + 独立数据分层 |
| 可信可审计 | 所有研判结果可溯源 | 消息、技能调用、记忆读写、模型调用全量留痕，靠 trace 串成树 |
| 人机协同 | 智能体出建议、人定决策 | 方案与简报签发为强制人工节点；置信度不足时自动熔断升级 |
| 环境无关 | 模型 / 存储 / 消息总线三处可替换 | 均通过配置切换，业务逻辑零改动 |

### 2.2 三条正交流

任何一次研判都由三条正交的流构成。把这个分层想清楚，整套架构就清楚了：

| 流 | 载体 | 回答的问题 | 可见位置 |
|---|---|---|---|
| **控制流** | Plan DAG | 谁在什么时候做什么 | 协同可视化页 · 任务图 |
| **数据流** | Message payload + Blackboard | 中间产物如何在智能体之间传递 | 协同可视化页 · 消息详情 |
| **记忆流** | 记忆的写入与检索事件 | 什么被记住、什么被复用 | 记忆中心页 · 记忆时间线 |

> **设计要点**：把「记忆流」独立成一条流，而不是藏在提示词拼接里，是本架构与普通检索增强生成方案的本质区别。前端能画出记忆流，才说明记忆系统是"有架构的"而非"塞了个向量库"。

### 2.3 层间约束

| 约束 | 内容 |
|---|---|
| 取数入口唯一 | 智能体不直连数据库，所有取数经技能层 |
| 数据分层只读 | 智能体只读标准数据层，读原始层视为越权 |
| 记忆写入唯一 | 只有记忆管家有权写长期记忆 |
| 原始数据不进上下文 | 只向模型提供特征与结论，原始行以引用形式传递 |
| 消息必留痕 | 每条消息落库，`trace_id` + `parent_msg_id` 构成因果树 |

## 3. Agent Card 规范

每个智能体以声明式卡片注册，由 Agent Registry 统一加载。卡片是智能体的「身份证 + 能力说明 + 资源画像」。

| 字段 | 类型 | 说明 |
|---|---|---|
| `agent_id` | string | 唯一标识，如 `A07_risk_assessor` |
| `name` / `role` | string | 名称与角色定位 |
| `description` | string | **供 Supervisor 做智能体选择**，需写清「什么时候该调用我」 |
| `capabilities` | string[] | 能力标签，用于任务路由匹配 |
| `skills` | string[] | 可调用的技能白名单，越权调用被拒 |
| `input_schema` / `output_schema` | JSON Schema | 强约束，输出不合法直接判失败 |
| `model_binding` | enum | `heavy` / `light` / `vision` / `embed` / `none`（纯规则） |
| `memory_access` | object | `read: [scope...]` / `write: [scope...]`，越权读写被拒 |
| `max_concurrency` | int | 并发上限，用于削峰 |
| `cost_profile` | object | 预估 token 与耗时，用于预算控制 |
| `permission_scope` | enum | 最低岗位要求（`operator` / `specialist` / `safety` / `admin`） |
| `failure_policy` | object | 超时阈值、重试次数、降级目标、是否可熔断到人工 |
| `version` | string | 版本号，进入审计记录 |

**为什么用声明式卡片而非代码继承**：卡片可以被扫描、校验、展示、热更新。前端能直接渲染成「Agent Card 画廊」——架构能力从抽象概念变成可指着讲的东西。

### 4.3 四个重点智能体的详细设计

#### A02 记忆管家 —— 系统里唯一有权写长期记忆的智能体

| 项 | 设计 |
|---|---|
| 触发方式 | ① 被 Supervisor 显式请求；② 订阅会话结束事件自动蒸馏；③ 定时任务执行衰减与巩固 |
| 读取流程 | 查询改写 → 多路召回 → 融合 → 重排 → 作用域与权限过滤 → 时效加权 → Top-K 组装 |
| 写入流程 | 候选抽取 → 归一化 → 相似去重 → 冲突检测 → 重要度打分 → 落库 + 建索引 + 事件广播 |
| **硬约束** | **长期记忆写入必须携带 `source_ref`（trace_id 或 message_id）与 `confidence`**，无来源的记忆不允许落库 |
| 失败降级 | 向量库不可用时退化为词法检索 + 元数据过滤，响应中标注 `retrieval_mode=degraded` |

详见 [02 记忆系统设计](02_记忆系统设计.md)。

#### A07 风险研判 —— 规则与模型混合，不是纯模型打分

采用三层打分，**前两层完全确定性**：

| 层 | 内容 | 权重 | 是否用模型 |
|---|---|---|---|
| 物理模型层 | 覆冰荷载、风偏裕度、雷击跳闸概率的公式化计算 | 0.45 | 否 |
| 规则约束层 | 阈值包判定、地形与冰区修正、合规检查 | 0.35 | 否 |
| 语义增强层 | 结合历史案例与文本描述做修正与解释 | 0.20 | 是 |

**输出硬要求**：必须包含 `risk_factors[]`，每项含 `factor_name / value / threshold / weight / contribution`。这是可解释性的硬约束，也是通过安全评审的前提。

**为什么不全交给模型**：① 公式计算可复算，模型输出不可复现，安全评审不接受；② 三层权重写入审计记录，复盘时可还原判断依据；③ 模型只在需要跨案例推理的语义修正项介入，且权重仅 20%。

#### A13 置信度评审 —— 熔断的唯一执行者

置信度由四路合成：

| 来源 | 权重 | 含义 |
|---|---|---|
| 模型自报置信度 | 0.30 | 语义层对自身判断的把握 |
| 数据质量分 | 0.30 | 治理层产出的数据可信程度 |
| 规则覆盖度 | 0.20 | 有多少结论有规则依据支撑 |
| 历史一致度 | 0.20 | 与历史同类情形的结论一致性 |

| 合成置信度 | 处置 |
|---|---|
| ≥ 0.75 | 直接通过 |
| 0.55 ~ 0.75 | 触发一次质询，要求补充证据（最多 1 轮） |
| < 0.55 | **熔断** → 终止自动链路，生成人工待办并标注熔断原因 |

所有评审结论落表，含被质询方、质询要点、修正前后对比。

#### A14 审批协同 —— 人机协同的记忆回填点

审批意见不是日志，而是**一等记忆**：

| 人工动作 | 生成的记忆 | 作用 |
|---|---|---|
| 采纳模型建议 | 程序记忆（该处理路径被确认有效） | 提高该路径的重要度，下次优先复用 |
| 修改后采纳 | 反思记忆（记录「模型建议 X，人工改为 Y」） | 下次同类任务作为反面参考注入 |
| 否决 | 反思记忆 + 用户行为记录 | 修正用户画像，调整该用户的输出偏好 |

这一设计让「记忆越用越准」形成闭环，是记忆系统价值的最终体现。

## 5. 编排模型：Supervisor + Blackboard + 点对点混合

| 模式 | 使用场景 | 优点 | 代价 | 本项目取舍 |
|---|---|---|---|---|
| Supervisor 层级委派 | 主链路（研判 → 简报） | 可控、可审计、易熔断 | Supervisor 是单点 | **主用**，符合责任链清晰的要求 |
| Blackboard 共享态 | 中间产物汇聚（特征表、风险表） | 避免消息风暴 | 并发写冲突 | **主用**，按智能体命名空间隔离 + 关键键占有机制 |
| 点对点 A2A | 评审质询、记忆读写 | 精准、低开销 | 需防死循环 | **限用**，质询上限 2 轮 |
| 事件广播 | 预警接入、审计留痕、前端推送 | 解耦 | 难追踪因果 | **限用**，仅用于通知类事件 |

### 5.1 为什么不用自由对话式多智能体

自由群聊（全员可见的对话）在演示上很好看，但在强监管场景下有三个不可接受的问题：

1. **责任链不可追溯**——对话图是多对多的网状结构，无法映射到「谁对哪个结论负责」；
2. **成本不可控**——每轮广播导致 token 消耗随智能体数量平方增长；
3. **终止条件模糊**——缺乏明确的收敛判据，容易陷入反复讨论。

因此本项目选择**显式的 DAG + 明确的消息路由**，牺牲灵活性换取可追溯性。这是场景决定的取舍，不是技术偏好。

### 5.2 Blackboard 并发控制

| 机制 | 内容 |
|---|---|
| 键命名空间 | `{agent_id}.{key}` 结构，默认仅写入者本人可改 |
| 跨智能体共享键 | 写入前需先 `claim`，持有者为唯一写者，其他智能体只读 |
| 占有超时 | claim 带 TTL（默认 30 秒），超时自动释放，避免死锁 |

## 6. 任务 DAG 示例

以覆冰橙色预警为例，一次完整研判的执行图：

```
T0  事件接入：气象中心推送覆冰橙色预警报文
      │
T1  A01 Supervisor：意图解析 → 生成 DAG → 预算核定（token / 时间）
      │
      ├──► T2a A03 数据治理：报文结构化 + 口径映射 + 质量校验        [并行]
      ├──► T2b A02 记忆管家：召回情节/语义/用户记忆                  [并行]
      │        └─ 命中示例：历史覆冰案例 + 覆冰阈值口径 + 值班员辖区偏好
      │
T3  A04 气象解析：气温 / 湿度 / 风速 / 相态 / 持续时长 / 覆冰增长速率
T4  A05 台账空间：空间相交初筛 → 候选区段 → 微地形暴露度分级
      │
T5  A06 历史案例：相似案例 Top-K + 相似度依据（地形 / 气象 / 电压等级）
T6  A07 风险研判：三层打分 → Top-N 高风险区段 + 因子拆解
```

## 7. 交付验收标准（架构层）

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 预警端到端全自动研判 | 一条指令触发，无人干预产出风险清单 |
| 2 | 数据口径映射生效 | 多套历史编码正确归并为统一标准编码，映射日志可查 |
| 3 | 数据质量问题被拦截 | 异常记录被隔离并给出原因 |
| 4 | 风险清单可解释 | 每条含 ≥3 个风险因子及贡献度 |
| 5 | 短期记忆跨轮次保持 | 同一会话第 3 轮仍记得第 1 轮的约束条件 |
| 6 | 长期记忆跨会话生效 | 新会话复用已沉淀的处理路径与口径 |
| 7 | 用户记忆个性化可见 | 切换用户后输出风格 / 默认辖区 / 模板变化 |
| 8 | 记忆可解释 | 任一结论可展开「本次引用了哪几条记忆」 |
| 9 | 多智能体消息全程可见 | 消息时序完整，含言语行为类型与耗时 |
| 10 | 熔断与人工升级可演示 | 置信度低于阈值时自动生成人工待办 |
| 11 | 简报自动生成 + 溯源 | 简报每段标注引用来源 |
| 12 | 全链路审计可回溯 | 任一结论可下钻至消息 / 技能 / 记忆 / 数据 / 模型版本 |
