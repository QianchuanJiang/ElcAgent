# 05 · 数据模型与接口规范

> 本文定义数据分层架构、核心表结构、规则包规范与对外接口契约。

---

## 1. 数据分层架构

采用四层分层，核心目的是**把数据质量问题隔离在进入模型之前**。

```
┌──────────────────────────────────────────────────────────────┐
│  原始层（各业务系统的原始数据，保留各自编码与格式差异）        │
│  设备台账 │ 地理信息 │ 气象 │ 缺陷库 │ 图像监拍 │ 微气象       │
└───────────────────────────┬──────────────────────────────────┘
                            │ 数据治理智能体
                            │ ① 编码映射  ② 字段校验  ③ 粒度对齐
                            │ ④ 单位归一  ⑤ 去重      ⑥ 异常隔离
┌───────────────────────────▼──────────────────────────────────┐
│  暂存层（清洗过程记录，可追溯每条数据的处理动作）              │
│  每行附：来源引用 / 治理时间 / 质量分 / 问题列表               │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│  标准层（口径统一的主数据，研判的唯一取数来源）                │
│  线路 │ 杆塔 │ 区段 │ 气象时序 │ 阈值规则                      │
└───────────────────────────┬──────────────────────────────────┘
┌───────────────────────────▼──────────────────────────────────┐
│  服务层（服务视图 + 记忆与审计）                              │
│  风险服务视图 · 岗位分级视图 · 记忆表 · 消息日志 · 审计表      │
└──────────────────────────────────────────────────────────────┘
```

### 1.1 分层设计要点

| 要点 | 说明 |
|---|---|
| 质量问题只存在于原始层 | 一旦进入暂存层即被治理，标准层不含未处理的数据问题 |
| 清洗可追溯 | 暂存层每行携带来源引用与问题列表，能回答「这条数据被改了什么」 |
| 标准层唯一取数 | 智能体只允许读标准层与服务层，读原始层视为越权 |
| 映射表外置 | 编码映射存于独立表 + 配置文件，支持热更新，不需要重写上游系统 |

### 1.2 为什么做口径映射层而不是数据搬迁

上游系统的归属方各不相同，任何一方都无法单方面改造。因此治理层采取**映射而非迁移**：

- 保留上游原始编码（不修改、不回写）
- 建立「上游编码 → 标准编码」的映射关系
- 新增映射只需追加记录，不影响已有数据

这与「数据治理先行」的设计原则一致：先统一口径，再喂给模型。

## 2. 业务侧核心表结构

### 2.1 线路主数据 `std_line`

| 字段 | 类型 | 说明 |
|---|---|---|
| `line_id` | string | 标准线路主键 |
| `standard_code` | string | 标准线路编码（统一口径） |
| `line_name` | string | 线路名称 |
| `voltage_level` | string | 电压等级 |
| `region` | string | 所属地市 |
| `operation_unit` | string | 运检单位 |
| `from_station` / `to_station` | string | 起止变电站 |
| `tower_count` / `span_count` | int | 杆塔数与区段数 |
| `length_km` | decimal | 线路长度 |
| `commission_year` | int | 投运年份 |
| `terrain_profile` | string | 地形剖面标签序列 |
| `historical_icing_flag` | int | 历史覆冰标记 |
| `sensitivity_level` | string | 数据分级 |
| `legacy_codes` | json | **各上游系统的原始编码（保留原文）** |
| `governed_at` | datetime | 治理时间 |
| `quality_score` | decimal | 治理后质量分 |

`legacy_codes` 结构（体现"不重写旧系统"）：

```jsonc
{
  "system_a": { "code": "LN-220-018",  "raw_name": "示例线路一线" },
  "system_b": { "code": "220kV_018#",  "raw_name": "示例线路1线" },
  "system_c": { "code": "018线",       "raw_name": "示例线路一线" },
  "system_d": { "code": "REG-018",     "raw_name": "示例线路一线" }
}
```

> 这四条在上游系统中是完全不同的字符串，治理层将其归并到同一个 `standard_code`。前端治理面板需要把这个归并过程可视化。

### 2.2 杆塔台账 `std_tower`

| 字段 | 说明 |
|---|---|
| `tower_id` / `line_id` / `tower_no` / `tower_no_std` | 标识与编号（含原始编号与标准化序号） |
| `longitude` / `latitude` / `altitude_m` | 坐标与海拔 |
| `tower_type` / `tower_height_m` / `span_length_m` | 塔型、塔高、档距 |
| `conductor_type` | 导线型号 |
| `terrain_class` | 微地形分类（垭口 / 迎风坡 / 背风坡 / 分水岭 / 平原 / 河谷） |
| `terrain_exposure` | 地形暴露度 0~1 |
| `wind_exposure_coeff` | 风压高度变化系数 |
| `icing_zone` | 覆冰分区（轻冰区 / 中冰区 / 重冰区） |
| `lightning_density` | 雷暴日密度 |
| `municipality` | 行政归属 |
| `sensitivity_level` | 数据分级 |

### 2.3 区段 `std_span`（研判的原子单位）

| 字段 | 说明 |
|---|---|
| `span_id` / `line_id` | 标识与归属 |
| `start_tower_id` / `end_tower_id` / `span_index` | 起止杆塔与序号 |
| `length_m` / `midpoint_lon` / `midpoint_lat` | 档距与中点坐标（用于空间相交） |
| `max_altitude` / `min_altitude` | 高程极值（用于微地形修正） |
| `terrain_class` / `terrain_exposure` / `icing_zone` | 地形与冰区属性 |
| `design_icing_mm` | **设计覆冰厚度（风险判定的基准值）** |
| `design_wind_speed` | 设计风速 |
| `windage_margin_m` | 风偏设计间隙裕度 |
| `critical_flag` | 历史高风险区段标记 |
| `municipality` | 行政归属 |

> **为什么以区段而非杆塔为研判单位**：档距跨度小、气象条件空间相关性强。逐基杆塔打分会造成结果碎化，也不符合运维按区段派工的作业习惯。以区段为单位既贴合业务，又把候选集规模控制在一个可计算的范围。

### 2.4 气象时序 `std_meteo_15min`

| 字段 | 说明 |
|---|---|
| `ts` | 时间戳（统一时区与粒度） |
| `station_id` / `station_type` / `lon` / `lat` | 站点标识与位置 |
| `temperature_c` / `humidity_pct` / `pressure_hpa` | 温湿压 |
| `wind_speed_ms` / `wind_gust_ms` / `wind_dir_deg` | 风速、阵风、风向（**单位统一为 m/s**） |
| `precipitation_mm` / `precip_phase` | 降水量与相态 |
| `icing_mm` | 等值覆冰厚度（**核心观测量**） |
| `visibility_m` | 能见度 |
| `data_source` / `quality_score` | 来源与质量分 |

`precip_phase` 是覆冰研判的关键字段：**冻雨 + 低温 + 持续时长**构成覆冰增长的必要条件组合。

### 2.5 事件域表

| 表 | 用途 | 关键字段 |
|---|---|---|
| `fault_record` | 故障历史 | 故障类型 / 位置描述 / 停电时长 / 损失负荷 / 原因 / 关联天气事件 |
| `defect_record` | 缺陷库 | 发现方式 / 缺陷类型 / 严重程度 / 描述 / 处理状态 |
| `camera_snapshot` | 监拍记录 | 拍摄时间 / 图像路径 / 摄像头类型 / 天气标签 / 判读标注 |
| `meteo_alert` | 预警报文 | 发布时间 / 发布单位 / 灾害类型 / 等级 / 影响区域 / 有效时段 / **报文原文** |

> `meteo_alert.raw_text` 保留报文原文供语义解析；其他字段的取值未经规范化，由治理层统一口径。

## 3. 规则包规范

规则包以配置文件形式外置，支持热更新与版本管理。

```yaml
pack_id: icing
version: v1.0
effective_from: 2026-01-01
source_doc: "架空输电线路覆冰监测与融冰技术导则（简化为示例）"

rules:
  - rule_id: IC-001
    name: 覆冰启动阈值
    type: threshold
    field: icing_mm
    operator: gte
    value: 12
    severity: 高
    action: 建议启动融冰

  - rule_id: IC-002
    name: 覆冰增长速率告警
    type: threshold
    field: icing_growth_rate_mm_per_h
    operator: gte
    value: 3.0
    severity: 高
    action: 加密观测

  - rule_id: IC-003
    name: 冻雨持续时长判据
    type: compound
    conditions:
      - { field: precip_phase,  operator: eq,  value: 冻雨 }
      - { field: temperature_c, operator: lte, value: -3 }
      - { field: duration_h,    operator: gte, value: 4 }
    severity: 中
    action: 纳入高风险候选

  - rule_id: IC-004
    name: 重冰区修正
    type: modifier
    when:   { field: icing_zone,   operator: eq, value: 重冰区 }
    effect: { risk_score_delta: 0.10 }

  - rule_id: IC-005
    name: 垭口地形修正
    type: modifier
    when:   { field: terrain_class, operator: eq, value: 垭口 }
    effect: { risk_score_delta: 0.08 }

  - rule_id: IC-006
    name: 历史覆冰段修正
    type: modifier
    when:   { field: historical_icing_flag, operator: eq, value: 1 }
    effect: { risk_score_delta: 0.12 }

  - rule_id: IC-007
    name: 融冰需报安全监督审批
    type: compliance
    when:   { field: action_proposed, operator: eq, value: 启动融冰 }
    effect: { require_approval: ["安全监督"], sla_hours: 2 }
```

**规则类型说明**：

| 类型 | 语义 |
|---|---|
| `threshold` | 单字段阈值判定 |
| `compound` | 多条件组合判定 |
| `modifier` | 对风险分做增量修正（体现微地形与冰区影响） |
| `compliance` | 合规约束，触发审批流 |

**三个规则包**：覆冰、风偏、雷击。规则包版本号进入审计记录，复盘时可还原当时依据的规则版本。

## 5. 接口契约

### 5.1 服务端接口分组

| 分组 | 主要端点 | 用途 |
|---|---|---|
| 任务 | 创建任务 / 查询状态 / 获取结果 / 导出 | 研判工作台 |
| 协同 | 获取 trace 树 / 获取消息序列 / 获取快照 / 回放 | 协同可视化与审计 |
| 记忆 | 列表 / 详情 / 检索实验 / 冲突列表 / 仲裁提交 / 记忆开关 | 记忆中心 |
| 用户 | 用户列表 / 切换身份 / 画像详情 | 全局 |
| 技能 | 注册表 / 健康度 / 启停 / 规则包读写 / 阈值试算 | 技能与规则页 |
| 简报 | 生成 / 分段重生成 / 差异对比 / 导出 / 提交审批 | 简报中心 |

### 5.2 实时事件流

WebSocket 单连接，服务端推送事件，前端以约 200ms 节流批量渲染。

| 事件 | 前端动作 |
|---|---|
| `task.created` | 创建任务卡片、初始化对比基线 |
| `plan.ready` | 渲染执行图骨架 |
| `agent.started` | 卡片进入运行态 |
| `msg.sent` | 时序图追加连线、消息流追加行、拓扑图高亮 |
| `skill.called` | 技能调用计数与缓存命中标记 |
| `memory.search_hit` | 亮起记忆标记、记忆时间线追加检索事件 |
| `memory.write` | 记忆时间线追加写入事件 |
| `critic.verdict` | 显示评审徽章；熔断时插入人工待办节点 |
| `arbitration.done` | 时间线追加仲裁事件 |
| `human.requested` / `human.decided` | 待办计数变化、提示记忆回填 |
| `agent.completed` | 卡片转完成态、更新指标 |
| `audit.appended` | Trace 树增量追加节点 |
| `task.completed` / `task.failed` | 结算对比指标 |
| `system.degraded` | 顶栏提示降级状态 |

**设计要点**：同一个事件既驱动前端动效，又作为审计留痕的原始记录。一份数据两处用，避免双写不一致。

### 5.3 消息信封

智能体间通信的信封结构见 [03 多智能体通信机制 · 第 3 节](03_多智能体通信机制.md)。所有内部通信、技能调用、事件广播共用同一信封。

## 6. 关于模拟数据

设计与开发过程中使用的**模拟数据仅用于代码调试与功能测试**，目的是让各模块在尚未对接真实业务系统时能够被独立验证。

此类数据：

- 不含任何真实企业信息、生产数据或个人信息；
- 不作为评估系统能力的依据；
- 不随本仓库分发。

本仓库只包含设计文档，不包含任何数据集。

### 6.1 更换为真实数据源时需要做的事

数据层的设计目标之一就是**让数据源可替换**。接入真实系统时，需要改动的仅是技能层的实现，业务逻辑与智能体定义均无需变更：

| 层 | 是否需要改动 | 说明 |
|---|---|---|
| 智能体定义（Agent Card） | 否 | 只声明需要什么技能 |
| 技能契约（输入输出 schema） | 否 | 契约不变 |
| 技能实现 | **是** | 由本地查询改为对接真实接口 |
| 数据模型 | 可能微调 | 字段扩充，不改变结构 |
| 记忆系统 | 否 | 与数据源无关 |
| 通信机制 | 否 | 与数据源无关 |
| 前端 | 否 | 通过接口契约解耦 |

这正是「技能是唯一取数入口」这条约束带来的收益。

## 7. 实现要点与常见陷阱

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 上游系统编码混用后直接聚合 | 聚合结果错误且难以定位 | 先建映射层，再聚合 |
| 2 | 在原始层之上直接做研判 | 数据质量问题带入模型，产生幻觉 | 治理先行，标准层唯一取数 |
| 3 | 映射表硬编码在业务代码里 | 新增映射需改代码 | 映射表外置，支持热更新 |
| 4 | 单位与粒度不做归一 | 数值量级错误，结论荒谬 | 治理层强制归一 |
| 5 | 溯源信息丢弃 | 无法回答「这个数从哪来」 | 暂存层保留来源引用 |
| 6 | 规则写死在代码中 | 阈值调整需发版 | 规则包外置 + 热更新 + 版本号 |
| 7 | 事件流与审计双写 | 两边不一致 | 一份事件两处消费 |
| 8 | 数据源耦合进业务逻辑 | 换数据源要改全系统 | 技能层隔离，契约不变 |
