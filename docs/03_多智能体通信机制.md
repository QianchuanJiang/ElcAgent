# 03 · 多智能体通信机制

> 通信机制是本项目的第二个核心模块。本文定义消息协议、通信模式、编排与仲裁规则、熔断降级机制与可观测方案。

---

## 1. 设计目标

多智能体系统的通信层要同时满足四个要求，缺一个都会退化成"函数调用编排"：

| 要求 | 判定标准 |
|---|---|
| **有协议** | 消息有统一结构，接收方能校验、能拒绝、能回执 |
| **有因果** | 任意一条消息能追溯到它的触发者，整条链能重建为树 |
| **有仲裁** | 多来源结论冲突时，有明确的裁决顺序而非随意取最后一个 |
| **有边界** | 超时、失败、置信度不足、预算耗尽时，有确定的降级路径 |

**判断是否真的实现了通信**：如果把消息总线改成直接函数调用（`target.handle()`），系统还能否正常工作？能，说明通信层是装饰；不能，说明通信层是真的。本项目要求后者。

## 2. 参考标准与取舍

| 标准 / 框架 | 借鉴点 | 不采用的部分及原因 |
|---|---|---|
| FIPA-ACL | 言语行为（performative）分类、会话协议 | 完整 ACL 过重，只取 10 个核心言语行为 |
| A2A Protocol | Agent Card 声明式能力描述、任务生命周期 | 本项目为单系统内协同，不需跨组织发现机制 |
| MCP | 技能的输入输出 schema 规范、工具调用形态 | 本项目技能为内建，MCP 作为对外暴露的可选扩展 |
| 状态图建模（如 LangGraph） | 状态机建模、检查点、可回放 | 借鉴建模思想，不引入其运行时（保持零框架依赖，便于讲清原理） |
| 对话式多智能体框架 | 多角色协作 | **不采用自由群聊**，理由见下 |

### 2.1 为什么放弃自由群聊式多智能体

自由群聊（所有智能体共享一个对话上下文、轮流发言）在演示上很直观，但在强监管行业场景下有三个硬伤：

| 问题 | 具体表现 |
|---|---|
| 责任链不可追溯 | 对话图是多对多的网状结构，无法回答「这个结论由谁负责」 |
| 成本不可控 | 每轮广播使 token 消耗随智能体数量近似平方增长 |
| 终止条件模糊 | 缺乏明确收敛判据，易陷入反复讨论或提前终止 |

因此选择**显式 DAG + 明确路由**的架构。这是场景决定的取舍：牺牲灵活性，换取可追溯性。

## 3. 消息信封规范

所有智能体间通信、技能调用、事件广播**共用同一信封结构**。这是整套通信机制的地基。

```jsonc
{
  "envelope": {
    "msg_id": "msg_01HZX...",
    "trace_id": "trc_01HZX...",
    "parent_msg_id": "msg_01HZW...",
    "session_id": "ses_...",
    "task_id": "tsk_...",
    "seq": 17,
    "sender": "A07_risk_assessor",
    "receiver": "A13_critic",
    "receiver_type": "agent",
    "performative": "PROPOSE",
    "intent": "risk_ranking_result",
    "ts": "2026-09-15T14:41:35.123+08:00"
  },
  "payload": {
    "risk_list": [
      { "segment_id": "...", "score": 0.87, "risk_factors": [] }
    ],
    "artifact_refs": ["art_..."],
    "data_refs": ["std_line_segment:..."]
  },
  "context_refs": {
    "memory_ids": ["mem_...", "mem_..."],
    "blackboard_keys": ["meteo.features", "asset.candidates"],
    "skill_calls": ["risk.calc_icing_load", "rule.eval_threshold_rules"]
  },
  "constraints": {
    "deadline_ms": 30000,
    "budget_tokens": 4000,
    "priority": "high",
    "must_use_skills": ["rule.eval_threshold_rules"]
  },
  "result": {
    "status": "ok",
    "confidence": 0.81,
    "evidence": [
      { "type": "data", "ref": "meteo_obs:icing:..." }
    ]
  },
  "telemetry": {
    "model": "glm-4.7-flash",
    "prompt_tokens": 1820,
    "completion_tokens": 640,
    "latency_ms": 2431,
    "cost_estimate": 0.0
  },
  "security": {
    "user_id": "u_002",
    "role": "specialist",
    "sensitivity": "internal",
    "allowed_zones": ["zone_a", "all"]
  }
}
```

### 3.1 信封的五个强制约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | `trace_id` 全局贯穿，`parent_msg_id` 构成因果树 | 审计回溯的唯一线索 |
| 2 | `context_refs.memory_ids` 必须声明本次决策**引用了哪些记忆** | 记忆可解释性的数据来源，不允许省略 |
| 3 | `result.confidence` 必须填写 | 置信度评审以此为基础之一 |
| 4 | `telemetry` 必须填写 | 分层调度效果与成本核算的依据 |
| 5 | 无 `source_ref` 的结论视为不可信 | 评审环节直接扣分 |

### 3.2 阶段性字段填充

三条流的不同阶段对信封字段的要求不同：

| 阶段 | 必填字段 | 可选字段 |
|---|---|---|
| 请求阶段（REQUEST / DELEGATE） | envelope + constraints + security | payload（部分） |
| 执行阶段（内部） | envelope + context_refs + telemetry | — |
| 响应阶段（PROPOSE / CONFIRM） | envelope + payload + result + telemetry | — |
| 失败阶段（FAILURE / REFUSE） | envelope + result.status + result.evidence（失败原因） | telemetry |

## 4. 言语行为（Performative）协议

| performative | 语义 | 典型使用 |
|---|---|---|
| `REQUEST` | 请求执行任务 | Supervisor → 执行智能体 |
| `DELEGATE` | 转派（含附加约束） | Supervisor → 子任务 |
| `QUERY` | 查询信息 | 任意 → 记忆管家 |
| `INFORM` | 通知事实（无返回值） | 各智能体 → 共享状态订阅者 |
| `PROPOSE` | 提交结论或方案 | 风险研判 → 评审 |
| `ACCEPT` / `REFUSE` | 接受 / 拒绝 | 评审 → 风险研判 |
| `CONFIRM` | 确认完成 | 执行智能体 → Supervisor |
| `FAILURE` | 报告失败与原因 | 任意 → Supervisor |
| `ESCALATE` | 升级到人工 | 评审 / Supervisor → 审批协同 |

**协议纪律**：

| 纪律 | 说明 |
|---|---|
| 每个 performative 有确定的响应集合 | 例如 `REQUEST` 只能被 `CONFIRM` / `FAILURE` / `REFUSE` 响应 |
| `REFUSE` 必须携带拒绝理由 | 前端与审计都需要理由，不允许静默拒绝 |
| `FAILURE` 与 `REFUSE` 语义不同 | 前者是执行失败，后者是权限或前置条件不满足 |
| `ESCALATE` 是终点 | 收到后自动链路终止，转入人工流程 |

## 5. 四种通信模式

| 模式 | 实现方式 | 使用规则 |
|---|---|---|
| **同步请求-响应** | 带截止时间的往返调用 | 强依赖顺序的任务（治理 → 研判） |
| **黑板共享** | 带版本的共享键值存储 | 大对象中间产物；写入需带命名空间 |
| **事件广播** | 发布订阅，无返回值 | 通知类：任务创建、审计追加、前端推送 |
| **定向会话** | 有限轮次往返 | 仅评审质询使用，**上限 2 轮** |

### 5.1 黑板并发控制

| 机制 | 内容 |
|---|---|
| 键命名空间 | `{agent_id}.{key}`，默认仅写入者本人可改 |
| 跨智能体共享键 | 写入前需 `claim`，持有者为唯一写者，其他智能体只读 |
| 占有超时 | claim 带 TTL（默认 30 秒），超时自动释放 |
| 冲突写入 | 记录日志并在前端提示，不静默覆盖 |

### 5.2 为什么需要黑板而不只用消息

如果把所有中间产物都通过消息传递，一个 47 个候选区段的中间表会在多个智能体之间反复序列化与传输，形成消息风暴。

黑板的定位是：**大对象走黑板，控制信息走消息**。这个分工让消息流保持轻量可读（前端时序图不会爆炸），同时大对象只被读写一次。

## 6. 编排流程与仲裁规则

### 6.1 编排主流程

```
Plan ──► Dispatch ──► [并行执行] ──► Join ──► Critique ──► (Replan) ──► Escalate?
                                                   │
                              ┌────────────────────┴────────────────────┐
                          通过 / 修正                            熔断 / 预算耗尽
                              │                                        │
                          进入下游                             生成人工待办
```

**关键点**：Plan 阶段生成的 DAG 是**按任务动态生成的**，不是预定义流程。同一个系统面对不同类型的请求（覆冰研判 / 大风研判 / 单区段查询 / 简报生成）应生成不同的执行图。这是「多智能体编排」与「工作流编排」的分界线。

### 6.2 仲裁规则（多来源结论冲突时）

按以下顺序裁决，先命中者胜：

| 顺序 | 规则 | 示例 |
|---|---|---|
| 1 | **硬规则优先** | 观测值超过阈值 → 无论模型如何判断，必入高风险 |
| 2 | **人工历史决策优先** | 上次同类情形人工判定为「暂不处置」，本次需给出差异化理由才能改变 |
| 3 | **置信度加权投票** | 多智能体给出不同结论时按各自置信度加权 |
| 4 | **重档模型复裁** | 前三者仍冲突 → 升级到重档模型重新推理一次 |
| 5 | **升级人工** | 仍无法裁决 → `ESCALATE`，生成待办，结论标记为待人工确认 |

**每次仲裁必须落表**，含参与方、各自结论、胜出方、胜出依据。这是可审计性在通信层面的体现。

## 7. 熔断、降级、重试与幂等

| 机制 | 触发条件 | 动作 |
|---|---|---|
| 超时熔断 | 单智能体超过 `deadline_ms` | 记 `FAILURE` → 重试 1 次 → 仍失败则降级 |
| 置信度熔断 | 合成置信度 < 0.55 | 终止自动链路，生成人工待办 |
| 数据质量熔断 | 数据质量分 < 0.6 | 拒绝进入研判，返回数据问题清单 |
| 预算熔断 | 累计 token 或耗时超预算 | 终止当前分支，保留已完成部分，上报 Supervisor |
| 循环检测 | 同一 `(sender, receiver, intent)` 三元组往返 3 次 | 强制中断并升级人工 |
| 模型不可用降级 | 推理服务异常 | 切换同构备用档位 → 仍不可用则回退规则与模板 |
| 检索降级 | 向量库异常 | 退化为词法 + 元数据检索，响应标注 `degraded` |

### 7.1 幂等

`msg_id` 作为幂等键，重复投递只执行一次。带副作用的技能调用会记录在调用日志中做去重。

### 7.2 重试

采用指数退避（200ms → 600ms），**最多重试 1 次**。次数刻意压低的原因：多智能体链路的延迟是累积的，重试次数过多会让端到端耗时失控。宁可快速降级，也不要长时间等待。

### 7.3 降级层级

技能层采用四级降级链，每级都标注当前降级层级供审计：

```
第 0 级：正常执行
第 1 级：结果缓存命中
第 2 级：简化算法替代（精度下降但可用）
第 3 级：返回默认值（明确标注为占位数据）
第 4 级：返回 FAILURE
```

## 8. 安全与权限

| 层级 | 措施 |
|---|---|
| 消息级 | 信封 `security` 携带身份与数据分级；接收方校验可见区域与角色，越权直接 `REFUSE` 并审计 |
| 智能体级 | Agent Card 的技能白名单与记忆权限，越权调用抛权限异常 |
| 技能级 | 技能声明最低岗位要求，调用前校验 |
| 数据级 | 敏感字段打标，跨智能体传输时脱敏（保留字段名与哈希） |
| 视图级 | 岗位分级视图：同一数据在不同角色下返回不同粒度 |

**权限校验发生在取数层而非展示层**。展示层过滤只是隐藏，取数层拦截才是真正的隔离。

## 9. 传输实现与可观测

### 9.1 传输分层（同一信封协议，三种实现）

| 环境 | 传输实现 | 说明 |
|---|---|---|
| 单机开发 | 进程内异步事件总线 | 零外部依赖，一键启动 |
| 单机多进程 | Redis Streams | 保留消费组语义，便于横向拆分智能体 |
| 集群 | NATS / Kafka | 生产方案，信封协议不变 |

**关键设计**：信封协议与传输实现解耦。换传输层不需要改动任何业务逻辑，只需替换总线的适配器。

### 9.2 事件类型

```
task.created      plan.ready        agent.started     agent.completed
msg.sent          skill.called      skill.returned    memory.search_hit
memory.write      critic.verdict    arbitration.done  human.requested
human.decided     audit.appended    task.completed    task.failed
```

这些事件同时是两个东西：前端实时动效的数据源，以及审计留痕的原始记录。一份数据两处用，避免双写不一致。

### 9.3 可观测三件套

| # | 组件 | 内容 |
|---|---|---|
| 1 | 消息日志表 | 每条消息完整落库（信封 + 载荷摘要 + 耗时） |
| 2 | Trace 因果树 | 由 `trace_id` + `parent_msg_id` 重建，可展开折叠、按耗时着色 |
| 3 | 实时推送 | WebSocket 订阅事件总线，前端以约 200ms 节流批量渲染 |

### 9.4 回放机制

一次任务的完整消息序列存为快照，支持按原始时间间隔或加速模式回放。

**回放不只是演示保险**——它在调试时同样有用：当某次研判结论异常时，回放能精确定位到哪一步的消息内容不对。

## 11. 实现要点与常见陷阱

| # | 陷阱 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 消息总线内部直接函数调用 | 无并发、无隔离、无法观测 | 信封序列化 → 总线投递 → 路由表分发 → 反序列化 |
| 2 | DAG 写死为顺序执行 | 退化为工作流编排 | Supervisor 按任务**动态生成**执行图 |
| 3 | 不记录 `parent_msg_id` | 无法重建因果树，审计断链 | 每次派生消息继承父消息 ID |
| 4 | 不声明引用的记忆 | 记忆可解释性失去数据来源 | `context_refs.memory_ids` 强制填写 |
| 5 | 无循环检测 | 两个智能体来回质询，token 烧尽 | 三元组往返计数 + 上限中断 |
| 6 | 消息里传大对象 | 序列化开销大，时序图不可读 | 大对象走黑板，消息只传引用 |
| 7 | 权限校验放在展示层 | 只是隐藏，未真正隔离 | 在取数层拦截 |
| 8 | 重试次数过多 | 端到端延迟累积失控 | 最多 1 次，快速降级 |
| 9 | 降级静默发生 | 审计无法还原真实执行路径 | 标记降级层级并落库 |
| 10 | 广播用于所有通信 | 消息风暴 + 因果链断裂 | 广播仅限通知类事件 |
