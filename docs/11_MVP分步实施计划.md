# 11 · MVP 分步实施计划

> 本文是 [CODEBUDDY.md](../CODEBUDDY.md) 的配套文档，给编码代理提供**逐步可执行的任务分解与验收标准**。
> 每完成一个里程碑，需按 `CODEBUDDY.md` §9.2 的格式汇报，等确认后再进入下一个。

---

## 0. 开工前的一次性动作

在写任何代码之前，先做这三件事，并一次性汇报给用户：

```
① 通读 docs/01、02、03、04、09、10（六份，其余按需）
② 把每份文档中「接口契约」「验收清单」「数据结构」三类内容摘出来，形成一张契约总表
③ 基于本文的里程碑划分，给出你的任务分解（哪些文件、什么顺序），并标出你认为模糊或冲突的点
```

**只做这一次确认，之后按里程碑推进，不要每步都回头问。**

## 1. 最小数据样例（"可以假"的部分）

MVP 阶段**不造数、不写生成器**。只需要以下硬编码样例，够验证机制即可：

| 样例 | 内容 |
|---|---|
| 线路 | 1 条，含标准编码 + 2 套历史编码（用于验证口径映射会真的发生） |
| 区段 | 4 个，含设计覆冰厚度、地形分类、冰区标记 |
| 气象时序 | 1 个站点 8 个时间点，含气温、湿度、风速、相态、覆冰厚度 |
| 阈值规则 | 3 条（一条阈值、一条组合、一条修正） |
| 记忆种子 | 6 条（语义 2、情节 2、程序 1、用户偏好 1，其中 2 条**故意互相冲突**） |
| 用户 | 2 个（不同岗位、不同辖区，用于验证用户记忆隔离） |

**要求**：这些样例直接写在配置或测试夹具里，**不要为了它们写导入脚本**。到 MVP 之后的阶段再做数据层。

## 2. 里程碑总览与依赖

```
M0 契约与骨架
   │  冻结协议层，后续不得随意改动
   ▼
M1 打通最小闭环 ──── 1 主控 + 1 执行 + 3 技能 + 1 条记忆
   │
   ▼
M2 动态执行图 ────── 8 智能体 + 能力模板 + 依赖推导 + 校验器
   │
   ▼
M3 三层记忆与记忆流 ── 预取/蒸馏时序 + 快照语义 + 冲突消解
   │
   ▼
M4 通信完整化 ────── 评审/熔断/仲裁/降级/循环检测/局部重规划
   │
   ▼
M5 技能治理 ──────── 权限/限流/缓存/降级层级/健康度/启停
   │
   ▼
M6 自检与可观测 ──── 15 条全绿 + trace 回放 + 事件流
```

**严格串行**：每个里程碑都依赖前一个的产出，不允许并行开工。唯一可提前做的是 M0 中与本步无关的配置骨架。

## 3. M0 · 契约与骨架

### 3.1 目标

冻结协议层，程序能启动并加载注册表，但**不含任何智能体逻辑**。

### 3.2 交付物

| 文件 | 内容 |
|---|---|
| `src/contracts/task.py` | 任务结构（字段定义见 `docs/08` §3.1） |
| `src/contracts/envelope.py` | 消息信封（见 `docs/03` §3） |
| `src/contracts/agent_card.py` | Agent Card（见 `docs/01` §3） |
| `src/contracts/skill_spec.py` | 技能声明（见 `docs/04` §2） |
| `src/contracts/capability.py` | 能力定义、能力需求模板、能力索引结构（见 `docs/09` §4.2、§4.3） |
| `src/contracts/plan.py` | 执行图节点、PlanRecord、ReplanRecord（见 `docs/09` §8） |
| `src/runtime/registry/` | 扫描 `config/`、校验 schema、加载注册表；冲突则拒绝启动 |
| `src/memory/store/schema.*` | 最小表集建表 |
| `src/model/router.py` | ModelRouter 骨架（先只支持 stub provider） |
| `config/skills_registry.yaml` | 3 个种子技能定义 |
| `config/agents/*.yaml` | 2 张 Agent Card |
| `config/capability_templates.yaml` | 1 个意图的能力需求模板 |
| `config/model_router.yaml` | 档位配置骨架 |
| `Makefile` | `check` / `test` / `verify` 入口 |
| `scripts/check_registry.py` | 启动自检 |

### 3.3 最小表集

```
memory_item          # 见 docs/02 §4.1
memory_edge          # 见 docs/02 §4.2
memory_access_log
message_log          # 见 docs/03 §10
skill_call_log
task / task_step
trace_snapshot
plan_record / replan_record / plan_rejection   # 见 docs/09 §8.2
```

### 3.4 验收标准

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | `make check` 可运行 | 输出「已注册 N 个智能体 / M 个技能 / K 个能力模板」 |
| 2 | 技能缺必填字段 | 启动被拒绝，错误信息指出是哪个文件、哪个字段 |
| 3 | 能力模板引用不存在的能力 | 加载被拒绝并指出引用位置 |
| 4 | Agent Card 引用未授权技能 | 加载被拒绝 |
| 5 | `make test` | 全部通过 |

### 3.5 允许简化

技能实现全部为空壳（返回固定值）；模型调用返回 stub；数据库用 SQLite 内存或临时文件。

### 3.6 禁止

写任何业务逻辑；写数据生成脚本；接入真实模型 API。

## 4. M1 · 打通最小闭环

### 4.1 目标

**1 个主控 + 1 个执行智能体 + 3 个技能 + 1 条记忆**，端到端跑通。

**这一阶段最重要的约束**：即使执行图只有一个节点，也必须走「意图 → 能力模板 → 能力索引 → 生成图」这条路。**不要为了快而先写顺序调用**——那会让 M2 变成推倒重来。

### 4.2 交付物

| 模块 | 内容 |
|---|---|
| `src/runtime/bus/` | 异步事件总线 + 路由表 + 投递与订阅 |
| `src/runtime/blackboard/` | 共享键值 + 命名空间 + 占有机制（占约带 TTL） |
| `src/runtime/supervisor/` | 最小调度器：模板 → 能力集合 → 图（可只有 1–2 个节点） |
| `src/runtime/trace/` | 消息落库、trace 重建 |
| `src/memory/` | 写入流水线（简化：归一 → 精确去重 → 落库）、检索（向量 + 词法融合）、访问日志 |
| `src/skills/` | **三个技能**：① 一个纯计算（如风险分公式）② 一个查表（如口径映射）③ 一个走 ModelRouter |
| `src/agents/` | 主控 + 1 个执行智能体 |
| `scripts/verify_m1.py` | M1 自检 |

### 4.3 验收标准

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 端到端执行 | 投一条任务 → 生成图（有 `plan_record`）→ 执行 → 调 3 个技能（有 `skill_call_log`）→ 写记忆（有 `memory_item`）→ 返回结果 |
| 2 | 因果树可重建 | 从 `trace_id` 能重建父子关系，节点数与 `message_log` 一致 |
| 3 | 记忆真的在起作用 | 写入后立即检索能命中；**把检索关掉，测试断言必须失败** |
| 4 | 执行图来自模板 | 断言图的节点是从能力模板推导出来的，而非硬编码 |
| 5 | 幂等 | 同一任务重复投递只执行一次 |
| 6 | 未授权调用被拒 | 执行智能体调用白名单外的技能 → 抛权限异常且留审计 |

### 4.4 允许简化

只有 1 个意图、1 个能力模板；图只有 1–2 个节点；记忆只有一种类型、去重只做精确匹配；不实现衰减与巩固。

### 4.5 禁止

把执行写成直接的顺序函数调用；跳过信封直接传对象。

## 5. M2 · 动态执行图

### 5.1 目标

扩到 **8 个智能体 + 3 个意图**，实现完整的图生成链路与契约校验器。

### 5.2 交付物

| 模块 | 内容 |
|---|---|
| `config/agents/` | 8 张 Agent Card（精简版编队，见 `docs/01` §4.2） |
| `config/capability_templates.yaml` | 3 个意图的模板（含 `required` / `conditional` / `optional` 三种模式） |
| `src/runtime/supervisor/` | 意图识别 → 能力需求推导 → 候选过滤（六步）→ 依赖推导 → 拓扑排序 |
| `src/runtime/validator/` | 契约校验器 8 条铁律（见 `docs/09` §7） |
| `scripts/verify_m2.py` | M2 自检 |

### 5.3 验收标准

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | **同一意图在不同深度下生成的图不同** | 三个深度的图可 diff 出结构差异 |
| 2 | 条件能力按条件启用 | 有/无某产物时，图中该能力出现/消失 |
| 3 | 模型幻觉被拦截 | 模板引用不存在的能力 → 校验器拒绝，记入 `plan_rejection` |
| 4 | 依赖边可解释 | 每条边能指出它由哪组 `inputs ∩ outputs` 产生 |
| 5 | 无依赖能力确实并行 | trace 中相关节点时间区间重叠 |
| 6 | 关闭某智能体 | 图中不再出现；若能降级则走备选，否则按 `required` 规则失败 |
| 7 | 权限越界被拒 | 校验器拒绝并说明 |
| 8 | 依赖成环被拒 | 拓扑排序失败即拒绝，不进入执行 |
| 9 | 深度超限被拒 | 校验器拒绝 |

## 6. M3 · 三层记忆与记忆流

### 6.1 目标

实现完整的三层记忆、六级时序、冲突消解与快照语义。

### 6.2 交付物

| 模块 | 内容 |
|---|---|
| `src/memory/store/` | 三层作用域（session / global / user）、七种记忆类型、衰减字段 |
| `src/memory/pipeline/prefetch.py` | 任务级预取（宽召回入黑板） |
| `src/memory/pipeline/retrieve.py` | 三路召回 + 融合 + 重排 + 作用域与权限过滤 + 时效加权 |
| `src/memory/pipeline/write.py` | 写入流水线七步（含冲突检测、重要度打分） |
| `src/memory/pipeline/consolidate.py` | 任务末尾统一蒸馏（四条判断标准） |
| `src/memory/pipeline/decay.py` | 衰减重算与归档 |
| `src/memory/conflict/` | 冲突消解（权威优先级五级 + `supersedes` 版本链） |
| `src/memory/snapshot.py` | 任务内快照（MVCC） |
| `scripts/verify_m3.py` | M3 自检 |

### 6.3 验收标准

**直接采用 `docs/10` §11 的 10 条验证清单**，另加两条：

| # | 验收项 | 通过标准 |
|---|---|---|
| 11 | 冲突消解与版本链 | 预置的两条冲突记忆可仲裁，旧版转 `superseded` 但**仍可查** |
| 12 | 用户记忆隔离 | 切换用户后注入的记忆集合不同，且检索结果不同 |

### 6.4 允许简化

重排模型可先用简单打分替代，但**必须标注 `retrieval_mode`**；向量化可用本地小模型或哈希向量（保持接口一致）。

## 7. M4 · 通信完整化

### 7.1 目标

补齐监督层与运行期容错。

### 7.2 交付物

| 模块 | 内容 |
|---|---|
| `src/runtime/critic/` | 置信度评审：四路合成 + 三档处置（通过/质询/熔断） |
| `src/runtime/arbitration/` | 仲裁五级规则 + `arbitration_record` |
| `src/runtime/fallback/` | 四级降级链 + `fallback_level` 记录 |
| `src/runtime/loopguard.py` | 三元组往返计数与中断 |
| `src/runtime/replan.py` | 局部重规划五步 + `replan_record` |
| `src/runtime/human/` | 熔断生成人工待办 |
| `scripts/verify_m4.py` | M4 自检 |

### 7.3 验收标准

**采用 `docs/03` §11 与 `docs/09` §10 的相关条目**，加上 `CODEBUDDY.md` 中 15 条验证清单里"通信"那 5 条：

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 故意让某智能体超时 | 观察重试 → 降级 → 状态变更的完整过程 |
| 2 | 同一三元组往返 3 次 | 被强制中断，不进入死循环 |
| 3 | 两智能体同写黑板同一键 | 占约机制生效，无数据错乱 |
| 4 | 广播事件多订阅者 | 都收到且互不阻塞 |
| 5 | 让某节点失败 | 观察到**局部重规划**，已完成上游未被重跑 |
| 6 | 重规划两次仍失败 | 升级人工，不无限重试 |
| 7 | 置信度低于阈值 | 熔断并生成待办，标注原因 |

## 8. M5 · 技能治理

### 8.1 交付物

| 模块 | 内容 |
|---|---|
| `src/skills/dispatcher.py` | 调度：schema 校验 → 权限 → 限流 → 缓存 → 降级 |

### 8.2 验收标准

15 条验证清单中"技能"那 5 条：

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 传非法参数 | 被 schema 拒绝，错误信息可读 |
| 2 | 白名单外的智能体调用 | 被拒并留审计 |
| 3 | 禁用某个技能 | 任务走完整降级链 |
| 4 | 相同入参调用两次 | 第二次缓存命中 |
| 5 | 超过限流阈值 | 被限流且不阻塞主链路 |

## 9. M6 · 自检与可观测

### 9.1 交付物

| 模块 | 内容 |
|---|---|
| `scripts/verify_all.py` | 合并 M1–M5 自检 + 15 条验证清单 |
| `src/runtime/trace/replay.py` | 从快照回放完整执行过程 |
| `src/runtime/events.py` | 事件流输出（先写文件，接口预留推送） |
| `Makefile` | `make verify` 一键全量 |

### 9.2 验收标准

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | `make verify` | **15 条验证清单全部通过** |
| 2 | trace 回放 | 能按原顺序重放一次任务的全部消息 |
| 3 | 事件流完整 | 关键事件（任务创建、图生成、技能调用、记忆命中/写入、评审结论、熔断、重规划、完成）均有输出 |
| 4 | 无回归 | M0–M5 全部验收项仍通过 |

### 9.3 完成即到来的检查点

M6 完成后，**三个核心机制的骨架已经是真的**。此时：

- 业务数据依然全是硬编码样例 → 正常，数据是"可以假"的部分
- 智能体依然用规则或模板代替模型推理 → 正常
- 技能实现依然返回固定值 → 正常

**只要 15 条验证清单全绿，就说明机制部分完成了。** 之后的业务化与前端属于另一个阶段。
